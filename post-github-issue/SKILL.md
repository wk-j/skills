## GitHub Issue Creator

Create clear, well-structured GitHub issues — for bug reports, feature requests, and questions.

### When to Use

Use this skill when the user asks to:
- Open / create / file a new GitHub issue
- Report a bug on GitHub
- File a feature request or enhancement on GitHub
- Turn findings, a task, or a question into a tracked GitHub issue

### Workflow

1. **Identify the repo** — Confirm the target `<owner>/<repo>`. Use the current repo (`gh repo view --json nameWithOwner`) unless the user specifies another.
2. **Understand the request** — Read what the user wants to report. Investigate as needed (search code, read files, check existing issues) so the issue is accurate and specific.
3. **Check for duplicates** — Search existing issues (`gh issue list` / `gh search issues`) before creating; if a matching issue exists, tell the user and offer to comment instead of opening a duplicate.
4. **Choose labels** — Decide the correct type label (and optional area label) based on the content (see Label Reference below). Discover the repo's real label vocabulary with `gh label list` first.
5. **Draft the issue** — Write the title and full body following the Format Rules and Issue Template. Note which labels will be applied alongside the draft shown to the user.
6. **Create the issue** — Post via `gh issue create` with `--title`, `--body`, and `--label`.
7. **Edit an existing issue** — When updating an issue body you previously created, use `gh issue edit <number> --body`. **Before editing, verify BOTH guards below — if either fails, do NOT edit the body; post a comment instead.**

   1. **Author guard** — Fetch the issue's author (`.author.login`) and confirm it matches the currently authenticated account (`gh api user --jq .login`). **NEVER edit an issue body created by a different user** — only edit issues you (the authenticated account) authored.
   2. **AI-attribution guard** — Confirm the issue body contains the `🤖 Issue generated by AI` footer. **NEVER edit a human-written issue body**, even one authored by the same account.

### Label Reference

Always check the repo's labels before assigning. Use `gh label list --repo <owner>/<repo> --limit 50` to discover the full label vocabulary the project uses, and prefer the repo's existing conventions over the names below.

Below is a common label taxonomy — adapt to whatever conventions the target repo already has. If the repo uses different label names, prefer those.

#### Type Labels (assign exactly one)

| Label | When to Use |
|-------|-------------|
| `type: Bug` | Something isn't working — errors, crashes, incorrect behavior |
| `type: Enhancement` | New feature or improvement request |
| `type: Documentation` | Improvements or additions to documentation |
| `type: Question` | Further information is requested |
| `type: Help Wanted` | Extra attention is needed |

#### Area / Component Labels (optional)

Many projects scope issues to a specific area (e.g. `api: <name>`, `module: <name>`, `component: <name>`, `area: <name>`). If the project uses such labels, assign one when the issue is clearly scoped to that area.

#### Label Assignment Rules

1. **Every new issue should have a type label** — determine it from the request content and assign it on creation.
2. **Area labels are optional** — only add if the issue clearly relates to a specific area.
3. **Don't invent labels** — only apply labels that already exist in the repo. If a needed label is missing, ask the user before creating it.

> If the repo has no labels defined yet, skip the label steps or ask the user whether to create a baseline.

### Format Rules

- **Language:** Match the language the project/team prefers, or the language the user used when asking. Keep technical terms like table names, field names, and API paths in English even when writing in another language.
- **Non-developer-friendly:** Issues may be read by business analysts, product managers, or other non-developers. If technical terms are used, always include a glossary section (as a blockquote or section near the top). Explain what values **mean in business context**, not just what they are technically.
- **Title:** Concise and specific — state the problem or request, not a vague topic (e.g. "Upload fails when siteid contains a slash", not "Upload bug").
- **Markdown allowed:** Use `##`, `###`, bullet points, inline code, checklists — GitHub renders markdown.
- **Length:** Enough to be actionable — for bugs include reproduction steps and expected vs actual; for features include the problem and proposed solution. No filler.
- **Structure:** Lead with glossary (if technical terms used), then the summary/problem, then supporting details (repro, expected/actual, proposal).
- **No filler:** Skip greetings and signatures — GitHub adds author and timestamps automatically.
- **AI attribution:** Always end the body with the footer below (outside any section).
- **Edit over re-create:** When updating an issue you created, edit the body in place with `gh issue edit` rather than closing and re-opening.
- **Never edit another user's issue body:** Only edit issues authored by the currently authenticated account AND carrying the AI footer — verify both before any body edit (see Workflow step 7).

### AI Attribution Footer

Always append this at the very end of every issue body:

```
---
🤖 Issue generated by AI (Claude <MODEL_NAME>)
```

Replace `<MODEL_NAME>` with the actual model name being used (e.g., `Opus 4.8`, `Sonnet 5`).

### Issue Templates

#### Bug Report

```markdown
> **Glossary:** (include when the issue uses technical terms — translate the label into the issue's language)
> - **{term}:** {plain-language explanation}

## Summary

{1-2 sentences describing the problem in business terms}

## Steps to Reproduce

1. {step}
2. {step}

## Expected

{what should happen}

## Actual

{what happens instead}

## Details (if known)

- {relevant file/table/field, e.g. `UserGroupService.java`}
- {logs, error messages, environment}

---
🤖 Issue generated by AI (Claude <MODEL_NAME>)
```

#### Feature Request / Enhancement

```markdown
> **Glossary:** (include when the issue uses technical terms)
> - **{term}:** {plain-language explanation}

## Problem

{what need or pain point this addresses, in business terms}

## Proposed Solution

{what to build or change}

## Alternatives Considered (optional)

- {alternative}

---
🤖 Issue generated by AI (Claude <MODEL_NAME>)
```

#### Question

```markdown
## Question

{the question, stated clearly}

## Context

{what prompted it — relevant code, files, or behavior}

---
🤖 Issue generated by AI (Claude <MODEL_NAME>)
```

### Examples

#### Bug Report

```markdown
## Summary

Upload fails when `siteid` contains a slash — the file is stored under the wrong path.

## Steps to Reproduce

1. Call the upload endpoint with `siteid=a/b`
2. Observe the stored path

## Expected

File is stored under the resolved site folder.

## Actual

Path-resolution collapses the double slash, so the file lands one level up.

## Details

- `UploadService.java` passes `siteid` straight through to the storage layer without sanitizing
- No site-existence validation happens before upload

---
🤖 Issue generated by AI (Claude Opus 4.8)
```

### Commands

```bash
# Identify the current repo
gh repo view --json nameWithOwner

# List all available labels
gh label list --repo <owner>/<repo> --limit 50

# Check for duplicates before creating
gh issue list --repo <owner>/<repo> --search "<keywords>" --state all
gh search issues "<keywords>" --repo <owner>/<repo>

# Create a new issue
gh issue create --repo <owner>/<repo> \
  --title "<title>" \
  --label "type: Bug" \
  --body "$(cat <<'EOF'
<issue body>
EOF
)"

# View an issue (includes current labels and author)
gh issue view <number> --repo <owner>/<repo>

# --- Before editing an issue body, verify BOTH guards ---

# Who am I? (the currently authenticated account)
gh api user --jq .login

# Guard 1 — author: fetch the issue's author; must equal the account above
gh issue view <number> --repo <owner>/<repo> --json author --jq .author.login

# Guard 2 — AI footer: body must contain the AI-attribution footer
gh issue view <number> --repo <owner>/<repo> --json body --jq '.body | contains("🤖 Issue generated by AI")'

# Edit an existing issue body — ONLY after both guards pass
gh issue edit <number> --repo <owner>/<repo> --body "$(cat <<'EOF'
<updated body>
EOF
)"

# Add / remove labels on an issue
gh issue edit <number> --repo <owner>/<repo> --add-label "type: Bug,area: api"
gh issue edit <number> --repo <owner>/<repo> --remove-label "type: Question"
```
